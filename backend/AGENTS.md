# 后端协作说明

## 当前技术栈

- Java 25
- Spring Boot 4.1.1
- Spring MVC；`application.yml` 已启用虚拟线程
- PostgreSQL、MyBatis-Plus（Boot 4 starter）；SQL 在 `sql/` 按业务模块手动维护，不引入 Flyway
- 基础包路径：`io.github.chalmery.loopcraft`

修改版本或配置前，先检查 `pom.xml` 和 `src/main/resources/application.yml` 中的实际内容。

## Java 代码结构与风格

- 按业务能力/功能分包，不要把所有 Controller、Service、Repository 分别堆进全局大包。相关代码优先放在同一能力边界内；只有跨能力复用且确实稳定的内容才上移。
- 包名全小写，类型名用 `UpperCamelCase`，方法和字段用 `lowerCamelCase`，常量用 `UPPER_SNAKE_CASE`。一个 Java 文件只放一个主要顶层类型，类型名与文件名一致。
- 根包统一为 `io.github.chalmery.loopcraft`。按实际功能逐步创建包，不预建空包。建议边界如下：
  - `agent`：ReAct 执行循环、轮次/状态，以及 Agent 级编排。
  - `mcp`：MCP 客户端与传输配置、连接生命周期、能力发现、MCP 工具适配和协议错误处理。MCP 专属实现集中在此包，不散落到通用 `tool`、`config` 或 `service` 包中。
  - `tool`：LoopCraft 自己实现的非 MCP 工具、工具定义和执行入口。MCP 暴露的工具仍由 `mcp` 负责接入，再通过清楚的边界交给 Agent 使用。
  - `web`：跨模块的 HTTP 基础能力，如请求日志、过滤器和通用异常映射；业务 Controller 和 DTO 优先放在各自功能包内，不在 Controller 中编排 Agent 轮次或直接实现工具。
  - `config`：Spring Bean 装配和基础设施配置；不放业务流程。
  - `shared`：仅放确实被多个能力共同使用、且不依赖某个具体能力的少量类型。不要把它变成 `common`/`utils` 杂物包。
- 以功能包为主，模块内按职责分包：`controller` 放接口与模块异常映射，`dto` 放请求/响应，`service` 放业务逻辑，`mapper` 放数据访问，`model` 放实体及业务数据类型，`config` 放模块装配。例如 `identity.controller`、`identity.mapper`；不要把这些类型全部平铺在模块根包，也不要跨模块集中到全局 Controller/Service/Mapper 包。只创建实际需要的子包，不为简单功能预建空层。
- 依赖方向保持清楚：Web 层调用应用能力；Agent 面向稳定的模型/工具边界；MCP 传输和协议细节封装在 `mcp` 内。避免循环依赖，不让底层适配器反向依赖 Controller。
- 使用 4 个空格缩进，不使用 Tab；保持方法短小、单一职责，条件分支优先使用早返回减少嵌套。导入使用明确的单类型导入，避免通配符导入。
- 语言特性以 `pom.xml` 声明的 Java 版本（当前 25）为准，不按旧版本习惯编写。内嵌 JSON、SQL 等多行文本一律使用文本块（`"""`）并保留结构缩进，不用转义或字符串拼接压缩成单行，牺牲可读性换紧凑不可取。
- 每行只放一条语句，字段和局部变量分别声明；构造器赋值、实体 setter、循环及 `try/catch/finally` 不压成单行。条件和循环体使用花括号，长条件拆成有明确含义的局部变量或私有方法；这些要求同样适用于测试代码。
- 参数名表达实际含义和单位，例如 `tenantId`、`skillId`、`baseVersion`、`requestId`，不以 `tenant` 表示 ID、`request` 表示请求标识。不要依据中文字段标签选择校验逻辑；名称与描述等规则差异应通过明确参数或专用校验方法表达。
- 默认使用构造器注入；依赖字段声明为 `final`。简单、不可变的数据载体可用 `record`；不要为少量字段创建多层无意义包装。
- 优先使用局部不可变数据和明确类型。对外请求和配置边界做校验；不要用 `null` 表示多种业务状态，不要用宽泛 `catch (Exception)` 吞掉错误，也不要把失败伪装成成功结果。
- 不为转发调用而新增没有业务含义的 `*Service`、`*Manager`、`*Helper` 或静态工具类。抽象应对应真实边界、复用需求或可替换实现。
- 注释以简短中文为主：业务类说明用途，Controller 接口方法说明操作与关键权限，实体/DTO 中含义不明显的字段说明业务含义、单位或枚举取值。通常一行即可，不逐个注释 getter/setter，不堆长篇说明。
- 关键逻辑的注释解释原因、约束和不明显的决策，不重复代码字面含义；删除过时注释，不留下未兑现的 TODO。

## 接口校验与异常边界

- Controller 负责 HTTP 参数转换、入口校验和响应组装，Service 负责权限及业务规则。固定结构优先使用 DTO 和 Bean Validation；手动解析 multipart 中的 JSON 后仍须显式校验，不把反序列化成功等同于字段合法。集合校验覆盖空集合、空元素、数量与元素长度。
- 确需用 Map 表达 PATCH 的“未传、置空、赋值”时，限定允许字段并逐项校验类型，明确空值语义；不把任意 Map 作为常规请求 DTO。Service 的业务不变量也要覆盖后台任务等非 HTTP 调用。
- JSON 接口沿用 `ApiResponse`，HTTP 状态与失败含义一致。跨模块通用异常映射放在 `web`，身份模块仅维护身份专属处理；不要为了接入新模块，不断让 `identity` 的异常处理器导入其他业务 Controller。
- 捕获异常后保留失败语义。兜底异常处理和后台清理至少提供可关联的操作、追踪 ID 或业务 ID、异常类别；不静默丢失意外错误，也不直接输出上游异常消息、SQL、凭证或文件内容。可选元数据解析允许降级时，注明降级范围。

## 事务与外部资源

- 多表写入、权限相关的状态变更、版本基线与幂等检查放在明确的事务边界内；并发正确性依靠数据库约束、行锁或条件更新，不能仅依赖“先查再写”。条件更新检查影响行数，事务方法不要依赖同类内部调用触发代理。
- 数据库事务不能回滚对象存储操作。写入对象前明确回滚补偿，删除时保留可重试的对象引用；失败和进程中断后的恢复必须有实际路径，不能仅凭一次回调或日志宣称最终一致。持锁期间的上传、删除须有超时和工作量边界，不无条件扩大锁范围。
- 流优先使用 try-with-resources，临时文件保证清理；清理失败不得掩盖原始业务异常。受检异常可能出现在写入流程时，明确其回滚规则。
- 幂等键必须绑定租户、操作者与本次操作的有效载荷；相同键和相同请求可返回原结果，相同键但不同内容应冲突。明确参与比较的元数据和文件内容，避免只比较部分字段却接受一次新的业务意图。

## MyBatis-Plus 数据访问

- 每张业务表对应清楚的实体和 Mapper，Mapper 默认继承 `BaseMapper<T>`；普通 CRUD 使用框架方法，查询和更新条件优先使用 `LambdaQueryWrapper` / `LambdaUpdateWrapper` 或 `Wrappers.lambdaQuery()` / `Wrappers.lambdaUpdate()`，通过方法引用指定字段。
- 分页使用 MyBatis-Plus 原生分页及已配置的分页插件，不通过 `.last()` 拼接 `LIMIT/OFFSET`。排序字段由后端明确指定，不直接接收客户端 SQL 片段。
- 能用框架方法和清楚的批量查询表达时，不手写注解 SQL、XML SQL 或用 `.apply()`、`.inSql()` 等绕过。批量关联查询避免逐条查库；不要为简单操作引入额外的通用 Service 或联表框架。
- 仅在框架无法合理表达的数据库专用能力、复杂查询或有证据的性能需求下手写 SQL，并在对应方法附近用简短中文说明原因。例如首次初始化使用的 PostgreSQL 事务级锁。不要为了少量 SQL 再包装一套数据访问框架。

## 数据库命名与 SQL 文件

- 业务表名统一使用 `lc_` 前缀和小写下划线，名称表达业务含义，例如 `lc_user`、`lc_tenant`、`lc_tenant_member`；列名同样使用小写下划线，例如 `display_name`、`tenant_id`。实体类可采用清楚的业务名称，通过 `@TableName` 显式映射实际表名。
- 主键通常命名为 `id`，关联列使用 `<业务对象>_id`；创建/更新时间按需使用 `created_at`、`updated_at`。索引和约束名称采用能看出所属表或用途的小写下划线命名，避免无意义缩写。
- 每张表、每个字段都通过 PostgreSQL `COMMENT ON TABLE` / `COMMENT ON COLUMN` 添加简短中文说明；状态、角色、单位等不直观字段说明取值含义。中文用于说明，数据库标识符保留英文。
- SQL 按业务模块放在 `sql/<模块>/`，一个表一个建表文件，使用 `create_<业务表名>.sql` 命名，文件名省略 `lc_` 前缀，不加 `001_` 等数字前缀。例如 `sql/identity/create_user.sql`、`create_tenant.sql`、`create_tenant_member.sql`。该表的索引、约束和注释放在同一文件。
- 执行顺序与跨表依赖写在模块 README，例如先用户、租户，再成员关系；共享环境执行过的文件保持不变，后续结构升级新建用途明确、无数字前缀的文件，并更新 README。应用启动不自动执行 SQL，不引入 Flyway；脚本中不放真实账号或凭证。

## 实现约定

- ReAct 执行过程应清楚、显式：模型响应、工具决策、工具执行、观察结果、下一轮迭代。
- 当前提供账号、租户、租户供应商连接/模型、文件存储及 Skill 管理；Agent 循环尚未实现。模型目录查询和 Skill 管理属于管理能力，不能因此接管手写循环。
- 当前仅保留 `dev` 运行环境，配置在 `env/dev/.env`；常规测试使用无数据源的 `test`，数据库测试通过 `./scripts/check.sh integration` 使用一次性 PostgreSQL。不要让测试连接开发业务库。
- 后续接入模型时，不依赖框架自动工具调用接管手写循环。
- 运行预算必须由循环显式读取和执行，并将剩余运行时间约束到模型请求和工具调用；配置绑定成功不代表已经实现轮次限制、超时或取消。
- 工具执行与模型响应解析保持分离。执行前校验工具名称和参数，并限制循环次数和执行时长。
- 除非有明确需求，沿用现有 Spring MVC 技术栈。虚拟线程有助于并发处理阻塞 I/O，但不能替代超时、下游并发限制或 CPU 密集任务管理。
- 明确处理模型和工具错误。工具调用失败时，不要伪造成功结果或把失败包装成成功的观察结果。
- 只有在解决明确需求时才新增依赖，并说明它对手写 Agent 学习目标的影响。

## 身份与租户边界

- 沿用 Spring Security Session 与 CSRF。登录轮换 Session ID 并清除旧 CSRF 令牌；修改密码或启停账号后，旧会话必须失效。密码仅保存单向哈希，不返回密码、哈希或会话凭证。
- 平台管理员与租户角色独立；普通用户只能访问已加入的租户，管理操作由后端校验权限。新增租户业务数据必须有明确的租户归属，查询和修改同时校验成员权限及资源所属租户，不仅检查资源 ID。
- 创建租户与建立负责人关系在同一事务中完成，数据库限制每个租户最多一个负责人；成员接口仅向当前租户负责人开放，不能移除负责人；平台管理员身份不能代替负责人身份。负责人交接仅由平台管理员在后台租户编辑中执行，租户更新和角色变更在同一事务内完成，原负责人保留为普通成员。开放注册或引入其他认证体系需有明确需求。
- 后台租户与账号 CRUD 接口逐次校验平台管理员权限。分页返回记录及总数；不允许通过账号编辑提升平台权限。平台管理员禁止停用/删除，负责人账号删除前必须完成交接；租户删除保留关联业务数据的外键保护，失败时成员删除一并回滚。
- 首次管理员仅在显式启用且用户表为空时初始化；保留并发初始化保护，不提供默认管理员密码，不在后续启动中覆盖已有密码或提升权限。

## 环境、日志与测试隔离

- `dev` 只连接本地开发数据库；测试 Profile 使用独立配置。SQL 手动执行，并记录已应用的文件，不能假定 Git 提交等于数据库已升级。
- 常规测试不依赖数据库或真实模型；数据库兼容性使用一次性 PostgreSQL 验证，不用 H2 代替。测试入口不读取部署环境文件，并清除继承的业务凭证及日志路径覆盖。
- 默认不记录凭证、完整提示词、工具结果或可能包含这些内容的上游异常。追踪 ID 仅用于日志关联，不作为身份或业务授权依据；请求结束后清理上下文，异步传播需显式设计。

## Code Review Rules

- 检查是否存在压缩成单行的业务或测试代码、依赖展示文案的校验、未校验的手动 JSON 解析，以及跨业务模块扩散的通用异常处理。
- 涉及事务、上传或版本保存时，检查并发冲突、幂等载荷比较、回滚补偿和清理失败路径；按改动补充有行为断言的测试，不只断言调用成功。
- 如果业务模块把 Controller、业务逻辑、Mapper、DTO 等全部平铺，或新增代码缺少必要的简短中文说明，应按上述分包与注释约定调整。
- 如果普通 CRUD 或分页无必要地手写 SQL，或建表脚本未按表拆分、带数字前缀、缺少中文表/字段注释，应指出与上述规范的不一致。
- 如果某个框架或辅助组件接管了完整的 ReAct 循环，应指出；循环应保持可见并由用户掌控。
- 如果模型生成的工具调用缺少工具白名单、参数校验、循环次数上限或超时，应指出。
- 如果日志默认包含 API 密钥、完整用户提示词或完整工具结果，应指出。
