# 开发交接契约

这两个产物必须相互对应。讨论结论负责确定业务行为，原型展示信息结构与交互；原型中临时出现但未确认的选择不能自动升级成产品要求。

## conclusion.md 应解决的问题

按需求复杂度合并章节，但正文必须让新 Agent 回答以下问题：

1. 当前阶段是什么？原型评审到哪一步？什么已经由用户确认，什么只是实现建议，哪些问题会阻塞正式开发？
2. 用户为谁解决什么问题？当前范围、后续范围、明确排除什么？代码里已有的能力是什么，文件证据和核查基线是什么？
3. 业务对象、字段归属、关联、唯一约束、状态及迁移是什么？哪些删除、修改必须事务保护？失败后保留什么？
4. 每类角色可以读什么、改什么？租户、资源和身份分别如何校验？敏感字段如何输入、保存和返回？
5. 每个核心流程从入口到结束如何运行？至少写正常、拒绝/失败和恢复路径，不用“处理异常”“适当校验”等空话。
6. 后端接口的 method/path、请求字段、响应结构、分页、错误和副作用是什么？字段省略、null、空字符串、重复请求意味着什么？不要只列 URL。
7. 页面如何进、如何返回？新增/编辑/删除/禁用/导入是什么交互？加载、空状态、失败、无权限、窄屏和键盘操作如何呈现？对照原型入口。
8. 预计修改哪些已有模块、新增哪些能力？依赖、SQL手动执行顺序、配置、兼容性和实施顺序是什么？不能把“计划新增”写成“已经实现”。
9. 如何验证开发完成？给出可观察的 Given/When/Then 场景、相关检查命令及预期结果。原型检查与正式后端验证分开记录。
10. 开发 Agent 的启动指令是什么？无需会话上下文，直接读文档和原型即可开始。

可用 `B-xx` 表示业务规则、`UI-xx` 表示交互流程、`A-xx` 表示验收。只对需要追踪的条目编号，并让接口/页面/验收引用相关规则，避免为编号增加重复正文。

## 原型与文档的一致性

- 两者显示相同的需求标识和修订号。更新改变业务含义时，两边一起更新。
- 原型示例数据明确是假数据；不将占位模型 ID 当作供应商真实可用模型。
- 查询、导入、表单、状态切换和删除要能点击。后端结果用可切换示例场景模拟；不展示“已连接成功”来暗示真正调用过接口。
- 密钥只展示配置状态；示例密钥不保存到 localStorage/文件，也不放进 URL。
- 受引用删除保护等未来约束，原型若尚未表现，必须在交接文档写清差异。审阅完成前补齐会影响用户判断的差异。
- 原型能独立运行；文档给出从仓库根目录执行的启动命令、预览相对路径及端口冲突时的替代方法。目录不能依赖正式 frontend 的文件存在。

## 完成状态

- `draft`：主流程或关键范围尚在讨论。
- `review`：可供评审，含显式建议/待确认项；未获用户认可的页面也属于此状态。
- `ready-for-development`：产品关键决策及页面已经认可，无阻塞设计问题；开发授权另按用户当前请求判断。

不要把审阅状态当成部署授权，也不要在用户已授权实施时再人为制造一次批准步骤。
