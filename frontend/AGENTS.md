# 前端协作说明

## 当前技术栈

- React 19 与 TypeScript
- Next.js App Router（SSR）
- Tailwind CSS 4（通过 `@tailwindcss/postcss` 集成）
- shadcn/ui（`new-york` 风格、Radix 原语、组件源码随项目维护）
- Lucide React（通用图标）
- Bun
- Oxlint（代码检查）、Prettier（格式与 Tailwind 类排序）、TypeScript（独立类型检查）

修改依赖或构建配置前，先核对 `package.json` 和现有 Next.js / TypeScript 配置。不要仅为个人偏好更换工具链。

## 开发入口与完成标准

- 仓库根目录用 `./scripts/dev.sh up` 启动；前端单独启动和环境要求见本目录 `README.md`。
- 格式化用 `bun run format`，检查用 `bun run check`（格式、lint、路由类型生成与 TypeScript）。交付前从仓库根目录运行 `./scripts/check.sh frontend`，其中额外执行生产构建；改动仓库检查或 hooks 时运行 `./scripts/check.sh all`。
- 不能通过关闭规则、扩大 ignore、添加无原因的 disable 或类型断言消除错误。确需局部例外时解释原因，并缩小到对应文件或行。
- 交互行为变化需验证加载、成功、失败及键盘操作；布局或组件样式变化检查桌面、窄屏和移动端。纯文档改动无需浏览器检查，不为样式类名和简单封装编写镜像测试。
- Git hooks 复用仓库 `.githooks`：pre-commit 只读检查暂存内容，失败不会自动修复、暂存或提交；pre-push 检查当前工作区的完整前端。CI 用 `./scripts/check.sh frontend` 再检查检出版本，hooks 不替代 CI。

## Next.js 与请求边界

- `src/app` 只承载路由、布局、页面组合和 Next.js 约定文件。默认 Server Component；需要状态、事件、Effect 或浏览器 API 的最小交互边界才标记 `'use client'`。被该入口导入的普通展示模块不必重复标记。
- 传给 Client Component 的数据必须可序列化；服务端模块不得被客户端导入。只有确需暴露给浏览器的公开配置才能使用 `NEXT_PUBLIC_*`，密钥始终留在后端/服务端。
- 账户信息不能进入共享缓存。SSR 读取会话时只转发必要 Cookie，使用 `cache: 'no-store'`，不缓存用户或租户数据到模块级共享状态。
- 浏览器请求统一使用同源 `/api`，复用业务 API 模块的 Session / CSRF / 响应校验流程，不另建一套认证、token 存储或后端权限判断。前端隐藏按钮不等于后端授权。
- 本地状态先用 React；有真实跨组件共享需求再考虑共享状态方案。不要默认引入全局状态库、数据请求库、表单库或第二套 UI 框架。

## 用户通知与接口反馈

- 全局短暂通知使用 shadcn/ui 的 Sonner 组件；在根布局只挂载一个 `Toaster`，业务组件通过 `toast.success`、`toast.error` 等方法触发通知。
- 用户主动操作产生的成功结果（如保存、删除或切换工作区）使用全局成功通知；与具体表单字段或表单提交直接相关的错误显示在对应表单附近，便于用户定位和修正。登录失败等表单错误沿用此规则。
- 非表单操作的接口失败可使用全局错误通知。不要为页面初始化、后台自动刷新或其他无须用户感知的请求弹通知，也不要在同一失败上同时显示重复的行内错误和全局通知。
- 请求进行中的状态优先显示在触发操作的控件或局部区域；只有确实需要跨越较长时间反馈同一异步操作时，才使用 Sonner 的 Promise 通知。

## 组件、样式与图标

- 新增或调整任何前端功能时，先选择现成组件，再编写业务数据与交互。必须先检查项目已有组件及 shadcn/ui 官方组件、示例和组合方案；表格、表单、下拉选择、弹窗、分页、导航、通知等常见界面统一通过现成组件组合实现，不从零手写已有的基础控件或交互。本地尚未引入的组件按实际需求添加；只有现成组件确实无法满足时才做必要扩展，并说明具体缺口，避免另建一套组件体系。
- 通用控件优先使用 `src/components/ui/` 中的 shadcn 组件，业务组合放在所属 `features`。已有控件的变体集中用 `class-variance-authority` 定义，条件类名和覆盖统一使用 `@/lib/utils` 的 `cn`。
- 新增或调整下拉选择控件时，统一使用 shadcn/ui 的 `Select`，例如右上角的租户切换。触发器、弹层、选项、选中标记和滚动区域保持项目统一样式，不以浏览器原生 `select` 的默认弹层作为最终交付效果。先检查现有基础组件，缺少时按需引入官方组件，避免手写已有的常用交互；完成后检查长文本、长列表、禁用状态、键盘操作和窄屏布局。
- shadcn 的 `components.json` 指向当前 App Router、Tailwind 4 与 `@/` 别名。按需增加组件，不一次性安装全库；不要使用 `--overwrite` 覆盖已定制组件。生成后审查依赖、导入和样式，统一从 `@/lib/utils` 引入 `cn`，删除与现有工具重复的依赖。
- 基础组件以 shadcn/ui `new-york` 的中性色主题、变体和默认尺寸为基准，页面布局、表单、导航和弹层保持同一风格。优先沿用已有组件变体，避免业务页面反复覆盖组件高度、圆角和颜色。`globals.css` 的 `@theme inline` 是 Tailwind 和 shadcn 角色色的唯一映射入口。
- Tailwind 用于日常布局与交互样式；复杂局部规则可用 `<组件名>.module.css`。全局 CSS 只放主题 Token、基础元素和必要全局规则，不新增业务全局选择器。
- 字号、圆角使用下文尺度。常规间距使用 `1 / 2 / 3 / 4 / 5 / 6 / 8 / 10 / 12` 对应的 Tailwind 间距类；布局宽度、网格和定位可按实际响应式需求表达，不滥用任意值逃避设计 Token。
- 通用图标从 `lucide-react` 具名导入，按需打包，不建立全图标字符串注册表或继续手绘常见图标。装饰图标使用 `aria-hidden`；只有图标的按钮必须有 `aria-label`。
- 操作按钮明确 `type`；本项目 `Button` 默认 `button`，提交表单显式 `type="submit"`。复用可访问性原语处理弹层的标题、描述、焦点和关闭行为。

## 前端代码结构与风格

### 目录与模块边界

- 采用轻量的按业务功能组织方式：先按用户场景划分 `features/<功能名>/`，再按实际需要划分模块内部职责。相关组件、Hook、类型和 API 请求就近维护，不分别堆进全局目录，也不强制引入完整的 Feature-Sliced Design 层级。
- 功能边界以独立的用户流程和维护职责为依据，不直接照搬后端分包。例如登录与会话、个人资料、工作区与成员、平台管理可分别归入 `auth`、`profile`、`workspace`、`admin`；不要把所有账户相关功能长期集中在一个宽泛的 `identity` 目录中。
- 各目录按以下职责使用；表中是组织约定，目录按需创建，不代表当前代码已全部按此拆分。

| 目录                     | 职责                                                      |
| ------------------------ | --------------------------------------------------------- |
| `src/app/`               | Next.js 路由、布局和页面组合，遵守上文 Server/Client 边界 |
| `src/components/ui/`     | shadcn 基础控件                                           |
| `src/components/layout/` | 跨功能使用的导航、页头和页面框架                          |
| `src/components/`        | 其他确实跨功能复用的基础展示组件                          |
| `src/features/<功能名>/` | 对应业务功能的界面、状态、请求和类型                      |
| `src/lib/`               | 与具体业务无关的公共基础工具                              |

- 小功能允许直接放组件与 API 文件，例如 `Login.tsx`、`authApi.ts`。相关文件增长且职责分组能帮助定位时，再建立 `components/`、`hooks/`、`api/` 等子目录；不要求每个功能配齐这些目录，不为每个组件机械创建单独目录，也不预建空目录。
- 文件数量本身不是拆分标准。一个模块出现多个可独立维护的业务流程时，优先按功能拆分；一个组件同时承担布局、多个业务的状态和大量接口操作时，应把这些职责移回所属功能，页面或流程入口保留必要的组合与协调，避免将全部逻辑转移到一个同样庞大的 Hook 中。
- `components` 和 `lib` 不依赖具体 `features`。跨功能组合由页面、布局或明确的流程入口完成，避免功能模块循环依赖；共享代码按真实职责归属，不以通用目录作为无法确定归属时的默认位置。
- 不要因为单个调用就建立全局 `utils`、`hooks`、`types` 大杂烩。抽到共享目录前，确认它有多个实际调用方且含义对这些调用方一致。

### 文件与实现约定

- 文件名和导出保持可预测：业务 React 组件使用 `UpperCamelCase.tsx`；自定义 Hook 使用 `useXxx.ts`；纯工具和非组件模块使用 `lowerCamelCase.ts`。`components/ui` 保持 shadcn 的小写连字符文件名，`app` 保持 Next.js 约定。组件和 Hook 优先使用具名导出，页面和布局按 Next.js 约定默认导出。
- TypeScript 类型尽量贴近其所属功能；跨功能共享的类型才放在共享模块。外部/API 数据先按 `unknown` 接收并校验，再进入内部类型；不要用 `any` 或类型断言绕过边界校验。
- 组件负责一个清楚的界面职责。业务组件可组合局部子组件；当文件难以阅读、逻辑有独立职责或需要复用时再拆分，不按行数机械拆文件。
- Hook 只封装有状态行为或副作用；纯数据转换放普通函数。API 请求集中在对应功能的 API 模块或明确的事件流程中，不要让通用展示组件隐式发请求。
- CSS/Tailwind 类保持就近且易读；复用样式优先用语义 Token 和小型组件封装。避免为了缩短一行而引入抽象，也避免重复覆盖同一属性。
- 导入顺序保持一致：第三方依赖、`@/` 项目模块、同功能相对导入；类型使用 `import type` 或内联 `type`。副作用导入的相对顺序保持稳定，不自动排序导入。格式与类排序以本目录 Prettier 配置为准。
- 注释解释必要的设计原因或边界条件，不复述 JSX/函数本身；完成改动时清理无用代码、注释和未兑现的 TODO。

## 代码约定

- 使用函数组件和明确的 TypeScript 类型；避免 `any`，也不要用类型断言掩盖不确定的数据。
- 组件负责清楚的 UI 边界；可复用的展示组件保持轻量，不要过早搭建通用组件框架。
- 将状态放在实际需要它的最低共同组件。能从现有状态计算出的值直接计算，不再复制保存一份。
- 组件中保持视图逻辑易读；当 API、复杂状态或可复用行为出现后，再按真实边界拆分文件和模块。
- 处理异步请求时明确呈现加载、成功和错误状态；避免旧请求结果覆盖较新的用户操作。
- 使用语义化 HTML，保证键盘可操作、焦点状态可见，并为非文本控件提供可访问名称。
- 样式优先使用 Tailwind CSS 和清晰的组件结构。避免无意义的内联样式、重复覆盖规则和随意散落的颜色值。
- 页面需适配窄屏与宽屏；不要只针对单一桌面尺寸布局。

## React Hooks 约定

- 遵守 Hooks 规则：只在函数组件或自定义 Hook 的顶层调用 Hook，不要放在条件、循环或嵌套函数里。
- `useEffect` 用于同步外部系统，例如订阅、浏览器 API 或请求生命周期；不要用它同步派生状态或触发本可在事件处理函数中完成的逻辑。
- Effect 应声明真实依赖，并在订阅、定时器或请求需要时提供清理；不要为了消除依赖提示而关闭检查或隐藏依赖。
- 只有在复用有状态行为或封装明确的副作用时才抽取自定义 Hook；纯计算逻辑使用普通函数。
- 避免无必要的 `useMemo`、`useCallback` 和 `memo`。先有可观察的性能问题，再考虑缓存。
- 异步 Effect 要处理过期结果和清理；由用户操作触发的请求优先放在事件处理流程中。

## Code Review Rules

- 指出违反 Hooks 规则、隐瞒 Effect 依赖或用 Effect 维护重复派生状态的改动。
- 指出会让过期异步结果覆盖新状态，或缺少必要加载和错误反馈的改动。
- 指出不可通过键盘操作、缺少可见焦点或没有可访问名称的交互控件。
- 指出为了“通用化”而增加、但当前产品没有实际用例支撑的抽象和依赖。

## 视觉方向：shadcn 中性色 AI 工作台

LoopCraft 的整体页面和组件以 [shadcn/ui](https://ui.shadcn.com) 的中性色风格为参考：浅色背景、黑色主按钮、黑白灰层级、细边框和适中的控件尺寸。界面以阅读和理解 Agent 对话及执行轨迹为主，页面、导航、表单、卡片和通知保持统一的视觉语言。主题变量的组织参考 [shadcn Theming](https://ui.shadcn.com/docs/theming)，具体颜色与尺寸以下文项目约定为准。

### 固定色板

颜色必须使用以下语义色，不得在组件中自行挑选新颜色或使用任意色值。实现时将这些值集中定义为全局设计 Token，再通过语义化 Tailwind 类或 CSS 变量引用。

| Token            | 色值      | 用途                                  |
| ---------------- | --------- | ------------------------------------- |
| `canvas`         | `#FAFAFA` | 页面背景                              |
| `surface`        | `#FFFFFF` | 对话区、面板和输入框                  |
| `surface-subtle` | `#F5F5F5` | 次级区域、用户消息、代码/工具结果背景 |
| `surface-hover`  | `#EDEDED` | 可交互表面的悬停状态                  |
| `border`         | `#E5E5E5` | 默认分割线和边框                      |
| `border-strong`  | `#A3A3A3` | 强调边界、输入框聚焦前边界            |
| `text-primary`   | `#0A0A0A` | 标题和主要正文                        |
| `text-secondary` | `#525252` | 次要正文                              |
| `text-muted`     | `#737373` | 辅助说明、时间和弱提示                |
| `accent`         | `#171717` | 主操作、链接、当前选中项文字          |
| `accent-hover`   | `#262626` | 主操作悬停状态                        |
| `accent-soft`    | `#F5F5F5` | 选中项和轻量强调背景                  |
| `accent-border`  | `#D4D4D4` | 强调区域边框                          |
| `success`        | `#067647` | 成功状态文字和图标                    |
| `success-soft`   | `#ECFDF3` | 成功状态背景                          |
| `warning`        | `#B54708` | 警告状态文字和图标                    |
| `warning-soft`   | `#FFFAEB` | 警告状态背景                          |
| `danger`         | `#B42318` | 错误状态文字和危险操作                |
| `danger-soft`    | `#FEF3F2` | 错误状态背景                          |

### 视觉尺度

- 默认只支持浅色主题；不要根据系统设置自动切换暗色主题，除非用户另行决定。
- 正文使用系统无衬线字体栈，优先系统自带中文字体；代码、工具参数和执行轨迹使用系统等宽字体。不要默认引入远程字体。
- 字号只使用 `12 / 14 / 16 / 20 / 24 / 30` 像素这组尺度；常规正文、标签和按钮默认 `14` 像素，长文本阅读区可用 `16` 像素，移动端输入框可用 `16` 像素避免聚焦缩放。
- 按钮、输入框和选择框的默认高度为 `36` 像素；紧凑按钮 `32` 像素，大按钮 `40` 像素，图标按钮与同级控件等高。多行输入框随内容场景设置高度；触屏场景按需扩大可点击区域。
- 间距使用 `4 / 8 / 12 / 16 / 20 / 24 / 32 / 40 / 48` 像素尺度。表单项间距优先 `16`，卡片内边距 `16` 或 `24`；页面通过留白建立层级，避免普遍放大控件。
- 圆角只使用 `6 / 8 / 12` 像素：小控件 `6`，按钮和输入框 `8`，对话卡片和面板 `12`。
- 默认使用 `1px` 边框。普通面板不加阴影；弹层只允许轻微阴影，不用彩色光晕。
- 主操作使用近黑背景配白色文字；次级操作使用中性描边或浅灰背景，弱操作使用 ghost 变体。选中导航项使用浅灰背景与深色文字，链接通过下划线和交互状态保持可辨认。
- 焦点环使用中性灰色并保持清晰可见；成功、警告、错误色仅表示对应状态，不作装饰。Sonner 通知沿用相同的中性色表面、边框和文字层级。

### 明确禁止

- 不新增色板之外的颜色，不用 Tailwind 任意色值或组件内临时写入的十六进制颜色。
- 不使用渐变、霓虹色、玻璃拟态、背景模糊、发光描边、强投影或装饰性动效。
- 不为了视觉变化给每类 Agent 步骤分配不同鲜艳颜色；执行轨迹优先使用中性表面和统一强调色。
- 不在没有用户确认的情况下新增暗色主题、字体、字号、间距、圆角或阴影尺度。
- 如确有新语义色或尺度需求，先说明现有 Token 无法表达的场景并征求用户决定，再更新本节 Token 表。

### Code Review Rules

- 新增或调整表格、表单、弹窗、选择框等常见界面时，检查是否复用了项目或 shadcn/ui 的现成组件；指出绕过现成组件、无明确缺口就自行重写基础控件或交互的改动。
- 指出使用色板之外的颜色、任意颜色类、未经批准的暗色主题或视觉效果。
- 指出偏离已定义字号、间距、圆角和阴影尺度的样式。
- 指出业务页面无必要地覆盖 shadcn 基础控件尺寸，或使用靛蓝等额外品牌色作为主操作和选中态的改动。
- 检查状态色是否只用于对应语义，并确认文本、焦点和控件状态仍清楚可辨。
